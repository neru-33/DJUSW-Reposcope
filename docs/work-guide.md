# 작업 가이드

이 문서는 이슈를 받은 팀원이 필요한 문서와 참고 코드를 찾아 작업을 끝내는 방법을 정리한다. 무엇을 만들지는 기준 문서에 있고, 이 문서는 어디를 보면 되는지를 알려 준다.

## 1. 처음 읽을 순서

| 순서 | 문서                            | 읽는 이유                   |
| ---- | ------------------------------- | --------------------------- |
| 1    | [기여 규칙](../CONTRIBUTING.md) | 브랜치, 커밋, PR 규칙       |
| 2    | [작업 계획](work-plan.md)       | 일정, 내 영역, 작업 순서    |

| 4    | [화면 흐름](screen-flow.md)     | 화면 목록과 이동 경로       |

처음에는 1, 2를 끝까지 읽는다. 3~6은 내 작업에 필요한 절만 읽는다.

## 2. 번호 읽는 법

문서와 이슈는 번호로 서로 연결된다. 번호를 알면 관련 내용을 바로 찾을 수 있다.

| 번호   | 뜻              | 정의된 곳                       |
| ------ | --------------- | ------------------------------- |
| `T-01` | 작업            | 작업 계획 5장                   |
| `S-1`  | 수집 기능       | 기능 명세 4장                   |
| `R-1`  | 사용자 기능     | 기능 명세 5장                   |
| `V-1`  | 화면            | 화면 흐름 1장                   |
| `#11`  | GitHub 이슈, PR | 저장소 Issues, Pull requests 탭 |

예를 들어 이슈에 `T-31`, `R-3`, `V-3`이 적혀 있으면 작업 계획, 기능 명세, 화면 흐름에서 같은 번호를 찾아 읽는다.

## 3. 작업 순서

1. **이슈 고르기:** 내 영역 라벨의 이슈 중 선행 작업이 끝난 것을 고른다. 담당자를 나로 지정한다.
2. **기준 확인:** 이슈의 작업 번호와 기능 번호로 기준 문서의 해당 절을 읽는다. 아래 4장의 표에서 내 작업의 참고 위치를 찾는다.
3. **완료 조건 확인:** 이슈의 완료 조건을 먼저 읽고, 시험 방법을 정한 뒤 시작한다.
4. **브랜치 만들기:** 최신 `main`에서 `<타입>/<이슈번호>-<짧은-설명>` 브랜치를 만든다.
5. **구현:** 기준 문서와 다르게 만들어야 하면 먼저 이슈에 적고 팀과 정한다. 문서를 바꿔야 하면 같은 PR에서 고친다.
6. **PR 올리기:** PR 템플릿을 채우고 `Closes #이슈번호`를 적는다. 완료 조건을 하나씩 확인해 체크한다.
7. **리뷰 반영:** 리뷰 의견을 반영한 뒤 승인을 받아 Squash로 병합한다.

## 5. 연계 프로젝트 코드를 가져올 때

- 가져온 파일과 원본 경로, 원본 커밋을 PR 본문에 적는다.
- `student-github-dashboard`로 시작하는 자원 이름과 Parameter Store 경로는 RepoScope 값으로 바꾼다.
- 비밀값, 로컬 `.env` 값, 키 파일은 가져오지 않는다.
- 메시지 형식, 테이블 정의, 저장 규칙은 바꾸지 않는다. 바꿔야 하면 먼저 팀장에게 알린다. 두 프로젝트가 같은 형식을 써야 하기 때문이다.
- 가져온 코드가 우리 문서와 다르면 우리 문서를 기준으로 고치고, 다른 점을 PR 본문에 적는다.
- 사용한 외부 오픈소스는 `docs/oss-license-check.md`에 기록한다.

## 6. AI 도구 사용

AI 도구는 저장소 루트의 `AGENTS.md`를 읽도록 하면 기본 규칙을 따른다. 작업을 맡길 때는 참고할 문서를 직접 알려 준다. 문서가 많아 AI가 필요한 절을 놓치기 쉽기 때문이다.

### 요청 예시

```text
이슈 #20을 구현해 줘.
- 작업: T-10 Webhook 수신 Lambda 구성
- 기준: docs/feature-spec.md의 S-1, docs/work-plan.md 3장
- 참고 코드: Onezero-GDGoC-DJU/2026URP의 lambda/ingest/
- 지킬 것: 메시지 형식은 연계 프로젝트의 docs/contracts/sqs-message.schema.json과 같게
- 완료 조건: 이슈 #20의 체크 항목
먼저 구현 계획을 보여 주고, 내가 확인한 뒤 코드를 작성해 줘.
```

### 결과 확인

- 완료 조건을 하나씩 직접 시험한다. AI가 "완료"라고 한 내용도 다시 확인한다.
- 기준 문서에 없는 기능이나 테이블이 추가되지 않았는지 확인한다.
- 비밀값, 개인정보, 키 파일이 변경 내용에 없는지 확인한다.
- 문서와 주석에 AI와 나눈 대화 내용이 남지 않았는지 확인한다. 결과물에는 최종 내용만 쓰고, 바꾼 이유는 PR 본문에 적는다.
- 이해하지 못한 코드는 병합하지 않는다. 리뷰에서 설명할 수 있어야 한다.

## 7. 막혔을 때

- 1시간 이상 막히면 이슈에 시도한 내용과 막힌 지점을 적고 팀 채널에 알린다.
- 기준 문서끼리 맞지 않거나 문서에 없는 결정이 필요하면 이슈에 적고 팀장에게 묻는다.
- 일정 안에 끝내기 어려우면 정기 모임 전에 알린다. 작업 계획 6장의 축소 순서에 따라 범위를 조정한다.
